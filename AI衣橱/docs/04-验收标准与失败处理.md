## 二、指标表（写死）

| 类别 | 指标 | 线 | 判定方式 |
|---|---|---|---|
| 硬 | 方案只用衣柜内单品 | **20/20**，出现 1 次即整体不通过 | 集合比对 |
| 硬 | 同套内一个 slot 只有一件 | 20/20 | 唯一索引 + 校验器 |
| 硬 | 温度/季节不冲突 | 20/20 | 温度带 vs 单品 warmth/seasons |
| 硬 | 套数与 expect 一致（含"不足时如实少出"） | 20/20 | 计数 |
| 硬 | 输出 100% 可被 Pydantic 解析 | 20/20 | 解析异常计数 |
| 硬 | 理由引用真实属性 | ≥18/20 | 关键词命中 |
| 软 | 「这套能穿出门吗」人工 5 分制 ≥4 | ≥16/20 | 你自己 + 1 位朋友盲评 |
| 性能 | 单次生成 P95 | ≤12s | 日志 latency_ms |
| 性能 | 建档 10 张照片总耗时 | ≤90s | 日志 |
| 降级 | 4 类降级各自命中正确路径 | **4/4** | 日志 fallback 标记 |
| 体验 | 375px 无横向滚动、三态齐全 | 5/5 页 | 人工 |

> **人工盲评怎么做**：把 20 条 case 的 60 套方案截图打乱顺序，不告诉对方哪些是"应该通过"的，让对方只回答"能穿出门吗 1–5"。这是唯一能防止你自己给自己打分的方式。

## 四、四类失败处理（**这张表是简历里最值钱的一段**）

失败不是"报错页"，失败是**产品的一部分**。每一类都必须有：触发条件 → 技术动作 → 用户看到什么 → 对应 case。

### F1 · 识别置信度低（`IN`）

| 项 | 内容 |
|---|---|
| 触发 | 任一字段 confidence < 0.7，或 category 落不进枚举 |
| 技术动作 | 该单品 `needs_confirm=true` 入库，**不阻塞其余单品**；不参与生成，直到用户确认 |
| 用户看到 | 衣柜页该卡右上角标注「待确认」，点击展开只需选 2 项（品类 + 主色），默认值已预填 |
| 文案 | 「这件没看清，是**衬衫**还是**针织衫**？」（给出 2 个候选，不让用户从 8 个里挑） |
| 反面 | ❌ 让用户重新拍照 ❌ 猜一个入库 |
| case | A02 / A04 |

### F2 · 候选集不足 / 无合规组合（`FILTER`）→ **422**

| 项 | 内容 |
|---|---|
| 触发 | 过滤后候选 <3 件，或可组套数 <3 |
| 技术动作 | 返回 422 + `shortage_hint`（缺哪个 slot、缺什么属性），**不调用模型**（省钱且快） |
| 用户看到 | 不是错误页，是「方案页」的一种状态：能给的方案照常给，下方一段缺件说明 |
| 文案 | 「今天 8℃，你只有 1 件外套，配不出 3 套。缺一件厚外套（warmth ≥4）。」 |
| 反面 | ❌ 硬凑 3 套 ❌ 白屏 ❌ 只显示"生成失败" |
| case | C01 / C02 |

### F3 · 模型超时（`COMPOSE` → 降级）

| 项 | 内容 |
|---|---|
| 触发 | 20s 未返回，或重试 2 次仍超时 |
| 技术动作 | 切 `prompts/compose_fallback.v1.md` 的**规则模板**（按 slot 贪心 + 正式度排序），`degraded=true`，`fallback_type=timeout` |
| 用户看到 | 3 套"基础搭配"照常显示，顶部黄条明示 |
| 文案 | 「AI 暂时没响应，以下是按温度和场合挑的基础搭配，可能不够精致。」 |
| 反面 | ❌ 转圈等到 60s ❌ 静默降级（用户以为是 AI 给的） |
| case | C04 |

### F4 · 输出结构解析失败（`PARSE`）

| 项 | 内容 |
|---|---|
| 触发 | 非 JSON / 被 markdown 代码块包裹 / 字段缺失 / item_id 不在候选集 |
| 技术动作 | ① 剥壳（提取 ```json … ```）② 带错误原因重试 1 次 ③ 仍失败 → 走 F3 的规则模板，`fallback_type=parse_fail` |
| 用户看到 | 同 F3，但黄条文案不同 |
| 文案 | 「这次没生成好，已换成基础搭配。点「换一套」可以再试。」 |
| 反面 | ❌ 500 直出 ❌ 前端 try/catch 吞掉后显示空白 |
| case | C03 / C05 |

### 一票否决项（出现任一条，整轮验收作废）

1. 方案里出现衣柜外的单品（P2 红线）
2. 静默降级：用户看到的是兜底结果但界面没有标识
3. `evaluate.py` 里用 `try/except: pass` 把异常算作通过
4. 为了让 case 过，改 `expect` 或放宽校验器
5. 用 mock 数据跑通演示，但 `make dev` 的真实链路是坏的

## 五、报告模板（`docs/reports/eval_vN.md`）

```markdown
# eval v2 · 2026-11-20

## 总览
| 指标 | 值 | 线 | 结论 |
|---|---|---|---|
| 硬约束通过 | 19/20 | 20/20 | ✗ |
| 软指标可穿率 | 17/20 | ≥16 | ✓ |
| P95 耗时 | 11.4s | ≤12s | ✓ |
| 降级命中 | 4/4 | 4/4 | ✓ |

## 明细
| case | 结果 | 归因 | 耗时 | 失败摘要（实际 vs 期望，只写最小差异）|
|---|---|---|---|---|
| B08 | ✗ | FILTER | 8.1s | 15℃ 时候选集为 0，warmth≤2 的单品被 seasons 排除了 |
| ... |

## 本轮改动 vs 上一轮
- 改了什么：filter 从「区间包含」改为「区间重叠」
- 通过数变化：14 → 19
- 回归：C05 从通过转为失败（原因：……）

## 结论
还剩 1 类根因（FILTER 的 seasons 维度），下轮修。
```

**必须保留 `eval_v1` / `v2` / `v3` 三个文件**。它们构成的通过率曲线（14→19→20）比任何 self-claim 都强。
