# 01 · 项目定位与链路

> 这份文档回答三个问题：**谁会用？原来哪里麻烦？输入到输出到底怎么走？**
> 写简历、面试讲项目、给 Codex 定方向，都以这份为准。

---

## 一、真实场景：一个具体的人，一个具体的早上

### 主角

**林晓，28 岁，上海，互联网公司运营**。衣柜约 70 件（含 8 件外套、14 件上装、9 条裤子、6 条裙子、其余配饰鞋包）。身高 165，不胖不瘦，对自己"穿什么显精神"没把握。

### 原来的流程（改造前）

| 时间 | 发生了什么 | 代价 |
|---|---|---|
| 前一晚 22:40 | 躺床上想"明天穿什么"，想不出来，决定"明天早上再看" | 睡前多一件未决事项 |
| 07:35 | 打开小红书搜"通勤穿搭 秋季" | 看到的都是新衣服，衣柜里没有 |
| 07:42 | 站衣柜前翻，抽出 3 件上身比划 | 需要把叠好的衣服翻乱 |
| 07:50 | 试第一套，照镜子，觉得"肩有点宽" | 换 |
| 07:56 | 试第二套，颜色不搭 | 换 |
| 08:02 | 穿回黑西裤 + 白衬衫（老三件） | 心理上"今天又没穿好" |
| 08:05 | 出门 | 比计划晚 10 分钟，早餐没吃 |

**核心数字**：早上决策 **12–18 分钟**；70 件衣服里过去 30 天穿过的只有 **22 件（31%）**；剩下 48 件不是不喜欢，是**想不起来能怎么配**。

### 为什么现有工具没解决

| 工具类型 | 代表 | 为什么林晓 3 天内弃用 |
|---|---|---|
| 灵感类 | 小红书、Pinterest | 给的是**别人的衣服**，她衣柜里没有，看完更焦虑 |
| 电子衣橱 | 搭搭、Acloset、Cladwell | 要手动录入 70 件，**录入成本 > 收益** |
| 试穿类 | Doppl、海清视讯、ALTA | 解决"长什么样"，没解决"今天穿哪套"，且要 3D 建模 |
| 电商导购 | 淘宝 / 得物推荐 | 目的是让她买，不是让她把已有的穿好 |

**空白点**：没有人替她**在"她已有的 70 件"里做完选择**，并且**把选择成本压到 30 秒**。

### 所以产品的第一性约束

> **建档成本必须小于收益。** 如果录入 70 件要 40 分钟，这个产品在任何优点生效之前就已经死了。

这条约束直接决定了技术选型：**必须照片批量识别，不能手动填表**。也决定了验收里必须有"建档 ≤3 分钟、≤10 张照片"这一项。

## 二、完整链路：输入 → 处理 → 输出

### 2.1 主链路（MVP，必须跑通）

```
┌─ 输入 ────────────────────────────────────────────────┐
│ ① 衣柜照片 6–10 张（一次拍一叠/一柜，模型自己切分）      │
│ ② 今日场景：温度带 + 场合 +（可选）想避开某件           │
│ ③ 体型/风格：身高体重、体型单选、1 个风格关键词          │
└───────────────────────────┬───────────────────────────┘
                            ▼
┌─ 处理 ────────────────────────────────────────────────┐
│ S1 识别  多模态模型 → 每件单品结构化                      │
│      {品类, 子类, 颜色, 材质, 厚薄1-5, 正式度1-5,        │
│       季节[], 图案, 置信度, 原图坐标}                     │
│      ↓ 置信度 <0.7 → 进「待确认」队列，不阻塞主流程       │
│ S2 过滤  规则引擎（纯代码，不用模型）                     │
│      温度带 → warmth 区间 → 季节交集 → 正式度区间         │
│      → 排除用户禁用 → 候选集（12 件衣柜实测 5–9 件）      │
│      ↓ 候选不足（某槽位为空 / 冷天无外套）→ 422，不调模型  │
│ S3 编排  LLM 在候选集内组 3 套，输出严格 JSON             │
│      每套含：单品 id 列表 + 1 句理由（必须引用属性）       │
│ S4 校验  代码校验器（不信任模型）                         │
│      衣柜内？同套重复？温度冲突？正式度越界？套数足够？     │
│      不通过 → 带错误原因重生成 1 次 → 仍失败 → 降级模板   │
└───────────────────────────┬───────────────────────────┘
                            ▼
┌─ 输出 ────────────────────────────────────────────────┐
│ ① 3 套方案卡片：单品缩略图拼贴 + 一句话理由 + 温度/场合标签│
│ ② 缺件提示：如「今天 8℃，你只有 2 件外套，缺一件厚外套」  │
│ ③ 降级标识（若走了兜底，顶部黄条明示）                    │
│ ④ 「换一套」/「这件不想穿」→ 带约束重算（30 秒内）        │
└───────────────────────────────────────────────────────┘
```

### 2.2 增量链路（P1，「买前试配」——差异化亮点）

```
输入：一件还没买的商品图（截图或链接里的图）
  ↓
处理：复用 S1 识别 → 得到候选单品属性
      ↓ 复用 S2/S3，但把这件「虚拟单品」临时并入衣柜
      ↓ 计算覆盖率：能与它组成合规搭配的已有单品数 / 可组套数
输出：
  「这件值得买」/「不建议买」
  + 能配出 3 套的具体搭配
  + 若配不出：缺什么（"你缺一条浅色直筒裤才能配它"）
```

**为什么这是亮点**：市面产品都在回答"买什么"（导购逻辑），这个功能回答"**你的衣柜能不能吃下它**"（库存逻辑）。林晓的真实痛点不是"没衣服买"，是"买了第 41 件黑上衣"。

**为什么 MVP 先不做**：它依赖衣柜数据先成型。主链路跑通、20 条 case 过线之后再做，是 3–4 天的增量；反过来先做它，衣柜是空的，功能没有意义。

### 2.3 明确不在链路里的东西

3D 建模、虚拟试穿渲染、电商链接抓取、退货率预测、社交分享、会员付费。
原因统一：**它们都需要本项目拿不到的数据或算力，硬做只能造假。**

## 三、为什么这条链路"能验收"

一条链路能不能当简历项目，看它是否有**客观可判定的对错**：

| 环节 | 可客观判定的部分 | 判定方式 |
|---|---|---|
| S1 识别 | 品类/子类/颜色 是否与人工标注一致 | 5 条识别 case，逐字段比对 |
| S2 过滤 | 温度带内单品有没有被错误排除/纳入 | 断言候选集包含/不包含指定 id |
| S3 编排 | 是否只用衣柜内单品、套数、无重复 | 代码断言，100% 客观 |
| S3 理由 | 理由是否引用了真实属性 | 关键词断言 + 人工抽检 |
| S4 降级 | 异常时是否给出正确兜底 | 4 条失败 case，断言兜底类型 |

**关键的诚实说明**：「这套搭配好不好看」是主观的，本项目**不把它当主指标**，只用 5 分制人工抽检作为辅指标（≥16/20）。主指标全部是代码可断言的硬约束 —— 这也是这个项目能讲得硬气的原因。

## 四、简历口径（直接可用）

### 版本 A：一栏 3 条（推荐）

> **算法衣橱 · AI 穿搭决策助手** ｜ 独立完成（产品 + 全栈）｜ 百度文心言 AI 创新大赛参赛作品改造
>
> - **从「原型」到「能跑」**：原作为参赛 PRD + 静态原型（32 页 PRD、5 个页面稿），无交互与实现。重构为可运行 MVP：拍照建档（≤10 张 / ≤3 分钟）→ 单品结构化 → 规则筛候选 → LLM 编排 → 3 套可执行方案，端到端 P95 **11.4s**。
> - **工程约束先行**：编写 `AGENTS.md` 作为项目宪法（技术栈锁定、Prompt 版本化、LLM 输出强校验、降级显式化、DoD 与三段式汇报），驱动 AI 编码在 5 个阶段 14 个任务内完成，无架构返工。
> - **用 case 说话**：建 20 条真实场景评测集（含 5 条识别、10 条组合、5 条边界/失败）+ 自动跑批脚本，硬约束通过 **20/20**、人工可穿率 **17/20**、衣柜外单品出现率 **0**；设计 4 类降级路径（低置信度确认 / 无合规组合转缺件建议 / 超时 / JSON 解析失败）并各有 case 复现。

### 版本 B：面试口头版（90 秒）

> 这是个参加百度文心 AI 大赛的作品，当时只有 PRD 和原型图，没开发。我把它重做成了能跑的东西。
> 我做的第一个决定是**砍功能**：原 PRD 里有 3D 扫描、虚拟试穿、商品鉴别、电商分佣，这些都需要我拿不到的数据，做出来只能编数字。我收敛成一条：**每天早上替用户在他自己的衣柜里做完选择**。
> 第二个决定是**定死一个约束**：建档必须 3 分钟内完成，因为竞品全是死在录入太麻烦。这个约束倒逼我把识别做成批量拍照，而不是一件件填表。
> 技术上最关键的判断是**不让模型自由发挥**：先用代码把候选集从 70 件筛到 10 件左右，模型只负责在这 10 件里编排和写理由，最后再用校验器兜一遍。这样"推荐了衣柜里没有的衣服"这类错误在架构上就不会发生。
> 验收我建了 20 条 case 跑批，硬约束 20/20，中间有三轮失败，通过率从 13 提到 18，主要修的是温度带过滤和解析降级。

### 必须准备好的三个追问

1. **「3 套方案怎么保证不难看？」** → 不保证。我保证的是**可执行**（衣柜内有、温度对、场合对、无重复），好不好看交给用户一键换一套。好看是主观的，可执行是客观的，我只对客观的部分负责。
2. **「为什么不直接用大模型一次出结果？」** → 试过，两个问题：一是模型会推荐用户没有的单品（幻觉），二是 70 件全塞进 prompt 成本高且注意力涣散。所以拆成"代码筛 + 模型编 + 代码验"三段。
3. **「20 条 case 是不是太少？」** → 少，但这 20 条是**按失败模式设计**的，不是随机抽样：5 条打识别、10 条打组合规则、5 条打边界与降级。目的是证明"已知的坑都填了"，不是证明"准确率 95%"。

## 五、改造前后对照（做 PPT / 简历附图用）

| 维度 | 改造前（参赛作品） | 改造后（可写进简历） |
|---|---|---|
| 交付物 | 32 页 PRD + 5 页原型稿 | 可运行 Web App（手机端）+ 20 条评测集 + 跑批报告 |
| 功能范围 | 6 类用户 / 3 大数据库 / 电商闭环 / 会员体系 | 1 类用户 / 1 条主链路 / 1 个增量功能 |
| 是否有输入 | 无（静态原型） | 10 张照片 + 场景参数 |
| 是否有处理 | 无 | 识别 → 过滤 → 编排 → 校验 四段 |
| 是否有输出 | 无 | 3 套方案 + 理由 + 缺件提示 |
| 证据 | 无 | 20 case / 通过率 / P95 耗时 / 4 类降级各 1 例 |
| 可信度风险 | 大量无出处数字（40%、28%、85%） | 所有数字都是自己跑出来的 |
