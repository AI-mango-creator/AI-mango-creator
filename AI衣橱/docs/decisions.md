## D1 · 建档方式

**决策**：拍照上传 6–10 张照片批量识别为主；手动录入作为兜底路径，每件只需填「品类 + 主色」两项，其余字段允许为空。

**理由**：P1 约束（建档 ≤3 分钟）是整个产品的生死线。手动填 9 个字段 × 70 件 = 用户必然在 3 天内弃用，这是竞品（搭搭 / Acloset / Cladwell）共同的失败原因。因此录入方式不是交互偏好问题，是可行性问题。

**影响模块**：`app/services/extract.py`、`web/src/pages/Intake.tsx`、`POST /api/wardrobe/upload`

**若被推翻的连带影响**：改成纯手动录入后，P1 约束失效，目标用户必须重新定义为"重度衣橱管理用户"；20 条 case 里的 A01–A05（5 条识别用例）全部作废，识别链路可整体删除。

---

## D2 · 温度来源

**决策**：MVP 由用户手选温度带（热 ≥26℃ / 温 20–25℃ / 凉 15–19℃ / 冷 <15℃）+ 场合 4 选 1（通勤 / 约会 / 周末 / 客户会议）。天气 API 列为 P1-2。

**理由**：接天气 API 会引入定位权限、城市映射、超时重试、离线兜底四件事，约 2 天成本，且**不改变任何一条 case 的正确性**。MVP 要验证的是"筛选 + 编排"是否成立，不是"能不能自动感知温度"。

**影响模块**：`app/services/filter.py`、场景页

**若被推翻的连带影响**：接 API 后 filter 入参从 `band` 字符串变成数值 `temp_c`，但 `cases/cases.json` 本来就是用 `temp_c` 定义的，case 不用改；需要在 S2 前加一层 `temp_c → band` 映射，并把 API 失败兜底成手选。

---

## D3 · 一套方案必须包含什么

**决策**：

1. 每套必须含 `top + bottom + shoes` 各一件（`dress` 可替代 `top + bottom`）
2. `band ∈ (cool, cold)` 时必须有 `outer`
3. `band ∈ (hot, warm)` 时不出现 `outer`
4. `band == cold` 时 `top.warmth >= 3`（保暖内层）
5. 同一套内每个 slot 只能 1 件（DB 唯一索引 `(set_id, slot)`）

**理由**：这是"可执行"的最低标准，也是校验器**唯一**的硬断言来源。没有这五条，"3 套方案"就只是三段随机文字，无法被代码判定对错。

**影响模块**：`app/services/validate.py`、`prompts/outfit_compose.v1.md`、`outfit_items` 表

**若被推翻的连带影响**：若允许"只给上装+下装、不含鞋"，校验器断言全线失效，C05（同套重复 slot 拦截）无法复现；B01/B03 的 `must_have_categories` 断言也要改。

---

## D4 · 出几套、不够怎么办

**决策**：目标 3 套；候选不足时**如实少出**（1–2 套）并在响应里返回 `shortage_hint`；连 1 套都组不出时返回 **422 + 缺件建议**；任何情况下禁止为凑数而放宽 D3 的约束。

**理由**：P4 约束。用户拿到一套穿不出去的搭配，损害比"今天没有方案"大得多——前者会让用户认为产品不懂他，后者只是暂时没货。且 C01/C02 两条 case 就是为了证明这一点而存在。

**影响模块**：`app/services/compose.py` 返回值、`POST /api/outfits` 的 422 分支、方案页 empty 态

**若被推翻的连带影响**：改成"永远出 3 套"会让 C01/C02 直接失败，且这两条正是简历里"诚实性设计"的证据，删掉后验收体系少一块。

---

## D5 · 身材数据用不用、怎么用

**决策**：采集身高 / 体重 / 体型单选（H 型 / 苹果型 / 梨型 / 沙漏型），**只用于生成理由文案的风格提示**（如"高腰版型拉长腿部比例"），不参与任何筛选或校验。

**理由**：身材 → 版型的匹配需要专业规则库或标注数据，MVP 做不出来。硬加进去的结果是"看起来在算，其实在猜"，一旦被用户发现一次（比如 165cm 被推荐超长款），信任直接归零。宁可明确只做"文案层"，不做"决策层"。

**影响模块**：`profile` 字段、`prompts/outfit_compose.v1.md` 的 reason 生成部分

**若被推翻的连带影响**：真要做硬过滤需引入版型库 + 部位测量 + 尺码表，工时 +3 天，且**没有客观验收手段**（无法用 case 断言"这件是否合身"）——这与本项目的验收原则冲突。

---

## D6 · 识别错了怎么改

**决策**：任一字段 `confidence < 0.7` 或品类落不进枚举 → 该单品 `needs_confirm = true` 入库，**不参与生成**直到用户确认；确认界面只需选 2 项（品类 + 主色），默认值已预填；不阻塞其余单品继续建档。

**理由**：识别必然有错，问题不是消除错误，而是**让纠错成本低于重拍成本**。让用户改 2 项（约 3 秒）可以接受，让用户重拍或填 9 个字段不可接受。

**影响模块**：`app/services/extract.py` 后处理、`wardrobe_items.needs_confirm`、衣柜页卡片态、`PATCH /api/wardrobe/items/{id}`

**若被推翻的连带影响**：若要求"全部确认才能生成"，建档时长必然突破 3 分钟（70 件 × 逐件确认），P1 失效；若允许低置信度直接参与生成，B02/B03 会出现"因错判厚薄导致温度冲突"的随机失败，跑批结果不可复现。

## D7 · 模型栈（P0 阶段）

**决策**：

- **P0 只允许 2 类远程调用能力**：① 一个多模态 VLM 做单品结构化（图 → `items[]` JSON）；② 一个文本 LLM 做方案编排（候选集 → 3 套 + 理由）。两者可以是同一家同一模型。**"2" 指能力种类，不是调用次数**，调用次数预算见下表。
- **禁止**：本地下载模型权重、引入 Paddle / SAM / detectron2 / diffusers、任何 GPU 依赖、任何需要自建推理服务的组件。
- **P1**：虚拟试穿走托管推理 API，不自建、不下载权重。
- **P2**：PP-YOLOE+ 定位 / SAM 2.1 抠图 / PP-LCNet 分类 / Qwen2.5-VL 本地部署 / SCHP+DensePose / CatVTON 自部署，六项**只写进文档，不实施**，切换条件见 `docs/03` 附录。

**理由**（两条，都要能背出来）：

1. **本机跑不动**：MacBook Air M5 / 16GB 统一内存。7B 视觉模型全精度权重约 14–15GB，装下权重就没有 KV cache 空间；Paddle 与 detectron2 在 Apple Silicon 上的编译支持长期不完善。
2. **四段串联不可接受**：`检测 → 分割 → 分类 → 属性` 解决的是同一件事，串起来会误差累积（框偏 → 分割漏 → 分类错 → 属性错）且**失败无法归因**；延迟乘四，与 T5 的"建档 90s"目标冲突。单次 VLM 调用的属性边界不稳定的问题，用「枚举收敛 + 置信度阈值 + 待确认队列」消化，成本远低于堆模型。

**影响模块**：`app/llm/client.py`（唯一出口）、`requirements.txt`、T5 验收、`docs/03` 附录

### D7.1 · 调用次数预算（解决 C03/C05 与"2 次"的冲突）

**决策**：D7 的"2"指**能力种类**，不是次数。每类能力的调用预算如下，与 `AGENTS.md` §6.1 的 `max_retries=2` 保持一致：

| 场景 | 单次请求上限 | 构成 | 对应 case |
|---|---|---|---|
| 识别（每张照片） | 3 次 | 首调 1 + 重试 2 | A05 拒绝路径不重试；A02/A04 低置信度不重试（结果有效） |
| 编排（每次生成方案） | 3 次 | 首调 1 + 重试 2 | C03 解析失败重试 ≥1；C05 校验失败重生成 ≥1 |
| 超时后 | 0 次额外 | 超时即降级，不再重试（20s × 3 已远超体验阈值） | C04 |

**约束**：

1. **重试必须带错误原因**（把校验器的失败信息作为 user message 追加），禁止原样重发——原样重发只会得到同样的错。
2. 建档 10 张图允许并发，但**并发上限 3**，避免触发上游限流（限流错误不算重试次数，走独立退避）。
3. 所有调用记账到 `data/llm.log`，跑批报告要输出"单 case 平均调用次数"，用于成本复盘。
4. 因此 `evaluate.py` 的耗时统计必须包含重试时间，不能只算最后一次成功的延迟。

**这条不是新增范围，是对 D7 的解释**：避免"预算 2 次"被理解成"禁止重试"，从而让 C03/C05 无法实现。

---

**若被推翻的连带影响**：改本地部署需 GPU 机器 + 2–3 天环境搭建，T5 的 90s 建档目标需重新评估；且 20 条 case 的跑批从"分钟级"变成"小时级"，三轮迭代节奏不成立。

## D8 · 用户可改哪些识别字段（T3 PATCH 白名单）

**决策**：PATCH 只接受 `sub` / `colors` / `material` / `pattern` / `category` 五个字段。
`seasons` / `warmth` / `formality` / `confidence` 一律 422 拒绝，不接受"先改再说"。
编辑成功后：被改字段的 `sources` 置 `user`、`user_edited` 置 `True`、`needs_confirm` 随之清空。

**理由**（三条，按重要性排序）：

1. **`warmth` / `formality` 是规则引擎的判定依据**。用户若能改，只要把全部单品改成 `warmth=4` 就能让系统在 8℃ 出 3 套——"推荐的都是能穿的"这个核心承诺会被自己人拆掉。这两个字段只能由模型给、由代码筛。
2. **`seasons` 不能单独改**。它由 `warmth` + `material` 推导；只放开 `seasons` 而不放开 `warmth`，会出现"季节是夏天、厚薄是 4"的自相矛盾数据，而且用户会得到"我明明标了夏天，为什么不推荐"的困惑——比不能改更糟。
3. **`category` 必须放开**。品类判错会让一件单品彻底失效（衬衫被判成外套，就永远进不了 top 槽位），而品类是用户最有把握判断的。这是"识别纠错"唯一必须给的入口。

**连带修掉的死锁**：`filter.py` 把 `needs_confirm=True` 的单品排除在候选集外。若用户改完不放行，低置信度单品会永远进不了推荐——待确认队列永不清空。因此 `needs_confirm` 的派生规则定为 `confidence < 0.6 and not user_edited`，只有一处实现。

**影响模块**：`app/routers/wardrobe.py`（白名单与 422）、`app/models.py`（派生规则）、`web/src/pages/Wardrobe.tsx`（只暴露这五个字段的编辑入口）

## D9 · 鞋不参与温度带的 warmth 过滤

**决策**：`filter_spec` 新增 `warmth_exempt_slots: ["shoes"]`。名单内槽位的 `warmth`
不参与温度带过滤，能否候选只由 `seasons`（以及 `formality`、`excluded`）决定。
名单只存在于数据文件，`filter.py` 不得硬编码槽位名。

**理由**：

1. **鞋的保暖档位与上装不可通约**。`top`/`outer` 的 `warmth` 是"这件衣服多厚、能扛几度"，
   而鞋的冷暖主要由鞋面结构（单层 / 加绒 / 雪地靴）决定，且真正决定"夏天能不能穿"的是 `seasons`。
   用同一套 1–5 量表要求鞋，等于让模型在没有刻度的地方猜一个数。
2. **真实事故**（`docs/reports/t5b-real-vision-shoes.md`）：单层皮革板鞋被判 `warmth=3`，
   在 26℃ 以上被 `allowed_warmth["hot"]=[1,2]` 直接过滤，用户看到"我有这双鞋，系统说夏天没鞋穿"。
   归因实验证明唯一变量是 `warmth`：仅把 3 改成 2，该鞋立刻回到候选集。
3. **豁免必须窄**。只豁免 `warmth`，不豁免 `seasons`——冬靴仍被 28℃ 的
   `allowed_seasons=["summer"]` 拦下。这两条各有一条单测钉住，防止日后顺手把豁免范围放大。

**影响模块**：`app/services/filter.py`（`_WARMTH_EXEMPT` / `_warmth_allowed`）、
`cases/cases.json`（`meta.filter_spec.warmth_exempt_slots`）、`app/tests/test_filter.py`

**已知残留**：`shortage.requirements` 对鞋仍会输出 `warmth_min`，不影响功能但会误导缺件文案，已入 backlog。

## D10-b · 上传识别必须由用户确认

**决策**：所有上传建档的新单品一律`needs_confirm=true`，不按confidence高低放行。用户成功PATCH既有五字段（sub/colors/material/pattern/category）任一，或点“这是对的”显式确认后，由唯一派生规则清除待确认。未确认仍不进入S2候选。confidence继续由模型产出并落库，仅辅助展示，不由用户填写、不决定上传是否待确认。

**优先级与范围**：本条取代D6/D8中针对上传识别的置信度阈值放行规则，D1–D9历史原文保留；D8五字段白名单不变，D9鞋温度豁免不变。本条不批准手动建档属性默认值，原backlog所称D10手动提问仍待人类定稿。

**理由**：真实R02防晒服被判为top且confidence=0.95，旧0.6阈值挡不住高置信度错类目。现有识别校正只在category=outer时抬高warmth，判成top即绕过这一分支；D9鞋过滤豁免无法修复此类识别错标。模型不是属性权威，逐件一次确认能暴露错误，不靠阈值假装确认完成。

**数据与来源**：显式确认置user_edited=true（表示用户已处理），needs_confirm由代码派生；不改模型属性或将confidence来源伪标user。PATCH改动字段仍标user，系统标志标derived，已有corrections审计保留。“这是对的”不伪造字段编辑。确认接口按owner隔离且幂等。

**历史处理**：对已有上传审计且尚未user_edited的单品回填待确认；基准seed和已编辑/已确认单品不误改。迁移幂等，非NULL owner及legacy隔离维持。

**验收**：不改prompt/cases/冻结证据，以v2真实重跑九张，9/9待确认；五字段PATCH及“这是对的”两条路径均验证needs_confirm=false、落库且可再次读取。

## D10-c · 单品删除与历史引用清理

**决策**：删除单品采用硬删除，不引入软删标记。接口按owner隔离，删除其他设备的单品与不存在的单品均返回404，不暴露存在性；首次成功返回204，再次删除返回404。

**执行顺序**：在owner_lock与同一数据库事务内，先删除该item在outfit_items中的历史引用，再清理该owner没有剩余引用的outfit_sets，随后删除wardrobe_items记录，最后清理照片文件。sessions保留既有请求记录。当前没有历史方案页，历史引用只存在数据库中；未来T9换一套只读取删除后的剩余衣柜记录。

**共用照片**：同一照片可能识别出多件单品；只有该owner最后一件引用删除时才删除照片，不能让其余单品丢失图片。文件路径必须限制在该owner的uploads目录中，不能越界删除。

**界面**：卡片右上角提供删除按钮，二次确认文案为“删除后将从历史方案中移除，不可恢复”。请求中禁用按钮，失败保留卡片并显示中文错误，成功再移除。

**理由与验收**：目前没有历史展示需求，硬删除能避免已删衣物继续进入推荐；显式清理引用遵守现有外键约束，不需要改表或模型响应。验证跨owner404、重复删除404、引用及空方案清理、共用照片最后引用清理、失败回滚与前端保留卡片。
