# 02 · 与 Codex 的对话脚本（五阶段）

> 用法：**一个阶段一个对话窗口**。阶段之间用 git commit 收口。每个 prompt 可直接整段复制粘贴，不需要改写。
> 前提：仓库根目录已有 `AGENTS.md`，`docs/` 下已有本套文档。Codex 会自动读 `AGENTS.md`，所以 prompt 里不必重复技术栈和禁令。

---

## 阶段 0 · 开工前 15 分钟（人工，不用 AI）

```bash
mkdir algowardrobe && cd algowardrobe
git init
# 把这套文件放进仓库
cp -r <本包>/* ./
mkdir -p app web prompts cases scripts data/uploads docs/reports
printf 'data/\n.env\n__pycache__/\nnode_modules/\ndist/\n' > .gitignore
printf 'LLM_PROVIDER=openai\nLLM_API_KEY=\nLLM_MODEL=\n' > .env.example
git add -A && git commit -m "chore: 项目宪法 AGENTS.md + PRD 提炼 + 定位文档"
codex
```

**为什么先 commit 再开工**：后面每个阶段结束都要 commit。5–8 个 commit 的提交历史本身就是"迭代过程"的证据，面试时可以直接展示。这不是形式主义——它是你**唯一能证明"我没有一次性生成全部代码"的材料**。

## 阶段 1 · 需求对齐（只出结论，不许写代码）

### 目标

让 Codex 把 PRD 读薄，并**暴露出 PRD 里需要人拍板的空白**。这一阶段的产出决定后面所有事，不要赶。

### Prompt（整段复制）

```
先读这三个文件，读完再说话，不要写任何代码、不要创建任何文件：
- AGENTS.md（项目宪法）
- docs/prd-提炼.md（PRD 精简版）
- docs/01-项目定位与链路.md（定位与链路）

然后输出下面 5 个部分，用中文，尽量短，不要复述原文：

【1】核心用户与场景（5 句话以内）
谁、在什么时刻、因为什么麻烦、要完成什么、现在的替代方案为什么不行。

【2】链路拆解表
把「输入 → 处理 → 输出」每一步列成表格：步骤 / 做什么 / 用模型还是用规则 / 失败时会怎样。
特别标出：哪一步最容易出错，为什么。

【3】待决问题清单（10 条，按对实现的影响从大到小排序）
每条必须写成「问题 + 两个可选方案 + 你倾向哪个 + 理由」。
只问真正影响代码结构的，不要问措辞、配色、文案这种。

【4】你认为 PRD 里 3 个「想当然」的地方
逐条说明：原文怎么写的、为什么我认为实现不了或会翻车、你的替代做法。

【5】本阶段你最不确定的一件事
一句话。

约束：
- 不要提出 PRD 和定位文档里没有的功能。想加功能请写进【3】里由我决定。
- 不要写"建议后续优化"这种空话，要具体的判断。
- 不要创建任何文件，直接在这里回答。
```

### 预期产出

一张链路表 + 10 个待决问题 + 3 个风险点。

### 你必须亲自拍板的 6 件事（不要让 AI 决定）

| 待决问题 | 建议决策 | 为什么这件事必须你来定 |
|---|---|---|
| 衣柜录入是拍照还是手动？ | **拍照为主，手动为兜底** | 这是 P1 约束的落点，也是整个产品的生死点 |
| 温度从哪里来？ | **MVP 手选温度带（4 档），天气 API 放 P1** | 接 API 会引入定位权限、失败重试、城市映射，是 2 天的坑 |
| 一套方案必须包含哪些品类？ | **上装 + 下装 + 鞋，外套按温度可选** | 决定校验器怎么写，必须先定 |
| 出几套？出不够怎么办？ | **目标 3 套，不足时如实输出并说明缺什么** | 这是 P4 约束，直接对应验收 case |
| 需要用户身材数据吗？ | **要，但只用于"风格提示"，不参与硬过滤** | 身材→版型匹配需要专业知识库，MVP 做不了，硬做就是编 |
| 识别错了用户怎么改？ | **待确认队列，可改品类/颜色，不阻塞主流程** | 决定交互复杂度，也决定 S1 的输入输出结构 |

> 这 6 个决策就是面试里"你的产品判断是什么"的答案。**自己想，别抄**——被追问"为什么这么定"时，抄来的答案撑不过两个问题。

### 常见翻车

- Codex 会把 PRD 里的 6 类用户全抄一遍 → 打断它："只保留 2.1+2.4 交集，其他写在【3】里由我决定"。
- Codex 会在这一阶段"顺便"建个 `app/main.py` → 立刻让它回滚。**阶段 1 出现任何代码文件都是失败**。
- 待决问题问成"配色用什么"这种 → 要求重出，只问影响结构的。

### 收口

把 6 个决策写进 `docs/decisions.md`（自己写，30 行以内），然后：

```bash
git add -A && git commit -m "docs: 需求对齐结论与 6 项产品决策"
```

## 阶段 2 · 方案输出（三案对比，选一个，仍不写业务代码）

### 目标

把决策翻译成**可施工的图纸**：数据模型、API 契约、页面清单、时序。这一步做扎实，阶段 3 写代码会快一倍。

### Prompt（整段复制）

```
读 docs/decisions.md（我阶段 1 的 6 项决策），然后按 AGENTS.md 出技术方案。

先给三个方案做对比表，维度固定为：开发工时(人日) / 我的调试难度 / 演示成本 / 失败点数量 / 是否满足 P1-P4 约束。
A 纯前端 + 本地假数据（最快看到样子，但没有真链路）
B 前后端分离：React + FastAPI + SQLite + 真实模型调用（推荐基线）
C B + 队列/缓存/多模型（过度设计，用来对照）
给出你推荐哪个，一句话理由。

然后只针对你推荐的那个方案，输出 5 份图纸：

【1】数据模型
用表格：表名 / 字段 / 类型 / 约束 / 说明。
必须包含 wardrobe_items、outfit_sets、outfit_items、sessions 四张表（表名可调整，但四类信息要齐）。
标出每个字段是「模型产出」还是「用户输入」还是「代码计算」，这三者不能混。

【2】API 契约
表格：method / path / 入参(含类型) / 出参(含类型) / 可能的错误码。
错误码要区分：400 参数错 / 422 无合规方案 / 504 模型超时 / 500 其他。
每个接口标注 P95 目标耗时。

【3】页面清单
不超过 5 页，每页一句话职责 + 该页必须有的状态（loading/empty/error 具体长什么样，不是"显示错误"这种）。

【4】一次完整请求的时序
文字版即可，标出：哪里调模型、哪里是纯代码、超时点在哪一步、降级从哪一步开始。

【5】三个最可能翻车的技术点 + 你的规避方案
要具体到"我会这样写"，不要"需要注意"。

约束：
- 这一阶段不要写实现代码，不要创建 app/ web/ 下的文件。
- 不要引入 AGENTS.md 禁用清单里的任何组件。
- 每个表格都要能直接照着写代码，不要出现"待定"。
```

### 预期产出

`docs/03-MVP与技术方案.md`（让 Codex 直接写进这个文件，不要只贴在对话里）。

### 你的验收动作

1. **看数据模型里"模型产出 / 用户输入 / 代码计算"有没有混**。混了就会出现"置信度是用户填的"这种荒唐设计。
2. **看 API 有没有 422 无合规方案**。没有这个错误码，说明它没想清楚 P4 约束。
3. **看降级从哪一步开始**。理想答案：从 S3 开始降级，S1/S2 失败要单独处理。

### 常见翻车

- 方案 C 被它推荐了 → 直接否掉，理由：单机 MVP 上队列是负资产。
- 页面给到 8 个 → 砍到 5 个，多出来的写 `backlog.md`。
- 数据模型里出现 `user_id`、`created_by` 这类为多用户准备的字段 → 砍掉，MVP 单用户。

### 收口

```bash
git add -A && git commit -m "docs: 技术方案（数据模型/API/页面/时序）"
```

## 阶段 3 · 确定 MVP（砍到能做完，然后只做第一个任务）

### 目标

把方案切成**每个 ≤ 半天、可独立验收**的任务，然后**一次只做一个**。

### Prompt（整段复制）

```
读 docs/03-MVP与技术方案.md（里面已有「范围三层」和「任务清单前 6 项」的基线，你要做的是审它、补它、而不是无视它重写）。

【1】【2】【3】直接修订 docs/03-MVP与技术方案.md 的「一、范围三层」章节；【4】【5】写进新建的 docs/tasks.md。包含：

【1】P0 范围（必须做完才能演示）
只保留一条主链路：建档（拍照/手动兜底）→ 选场景（温度带+场合）→ 生成 3 套 → 查看/换一套。
逐项列出该链路涉及的接口与页面。

【2】P1 范围（做完 P0 有余力才做）
候选：买前试配、天气 API、历史记录、理由可点开看属性来源。
按「性价比」排序，说明排序理由。

【3】Out of Scope（至少 10 项）
逐项写：不做 / 为什么不做 / 如果非要做得先解决什么。
必须覆盖：3D 试穿、电商抓取、用户体系、社交分享、会员付费、多语言、深色模式。

【4】tasks.md 任务清单
表格：任务号 / 一句话描述 / 涉及文件 / 验收方式（跑什么命令或看什么现象）/ 预估半天/一天 / 依赖任务号。
要求：单个任务改动不超过 8 个文件；任务之间依赖关系必须无环；每个任务的验收方式必须是可执行的，不能写"功能正常"。

【5】第一个任务
单独说明任务 1 要做什么，并给出你将执行的具体步骤（3-5 步）。

约束：
- 这一阶段仍然不要写业务代码。
- 任务清单里不要出现"完善 XX""优化 XX"这种无法验收的描述。
- 如果某个任务你估计要超过 1 天，拆开。
```

### 然后单独发起（永远不要和上面的任务混在一次）

```
执行 tasks.md 里的任务 1。开始前先用 3 行复述：要做什么、验收标准、会碰哪些文件，等我确认。
确认后实现，完成后按 AGENTS.md §8 的三段式汇报。
```

### 你的验收动作（每个任务都做）

1. `git status` 看有没有改到任务范围外的文件。
2. 跑它给的验收命令，**不要信它说"已通过"**。
3. 手机尺寸（375px）开一遍页面，空/错/加载三态各看一次。

### 常见翻车

- **一次给你 6 个文件的全量实现** → 打断："只做任务 1，其余写 backlog"。
- **把 P1 顺手做了** → 让它 revert，P1 是留给"P0 提前完成"的奖励，不是顺手。
- **验收方式写"功能正常"** → 要求重写成具体命令，如 `curl -X POST /api/outfits -d @cases/req_c06.json | jq '.sets|length'` 期望 3。

### 收口（每个任务一次）

```bash
git add -A && git commit -m "feat(task-N): <一句话>"
```

## 阶段 4 · 项目测试（造证据，这是全项目最值钱的一步）

### 目标

把"我觉得能用"变成"20 条 case 里 18 条过"。**这一步的产物直接写进简历。**

### Prompt（整段复制）

```
读 docs/01-项目定位与链路.md 第三节（为什么这条链路能验收）和 cases/cases.json。

现在做三件事，按顺序：

【1】补全 cases/cases.json 到 20 条
分布必须是：识别类 5 条、组合类 10 条、边界与失败类 5 条。
每条字段：id / type / title / input / expect / fail_policy / why_this_case（为什么这条 case 值得存在）。
组合类 case 的 expect 必须写成可断言的断言，例如：
  must_use_any_of: [W07, W12]（必须含保暖层）
  must_not_use: [W10]（28℃ 不许出现风衣）
  must_have_categories: [top, bottom, shoes]
  set_count: 3
不要写"搭配合理"这种无法断言的话。

【2】写 scripts/evaluate.py
- 逐条跑 case，对识别类调 S1、对组合类调 S2+S3+S4
- 输出 docs/reports/eval_v1.md，含：
  总览表（case_id / 结果 / 失败归因 / 耗时）
  分类通过率（识别 / 组合 / 边界）
  失败明细：每条失败写「实际输出 vs 期望」的最小差异
  汇总：硬约束通过数、P95 耗时、衣柜外单品出现次数
- 失败归因只能取这四类之一：IN（识别错）/ FILTER（候选集过滤错）/ COMPOSE（组合冲突）/ PARSE（解析失败）

【3】跑一次，把报告贴出来

约束：
- 通过标准写死在 docs/04-验收标准与失败处理.md，你先读它，不许改它。
- 不要为了让 case 通过去改 case 的 expect。
- 如果某条 case 是当前阶段实现不了的（比如依赖 P1 功能），标 status: "deferred" 并说明，不要伪造通过。
```

### 通过标准（已写在 `docs/04-验收标准与失败处理.md`，照抄一遍是为了让你记住，之后不许改）

| 类别 | 指标 | 线 |
|---|---|---|
| 硬约束 | 方案只用衣柜内单品 | 20/20，出现 1 次即整体不通过 |
| 硬约束 | 同套内无重复单品 | 20/20 |
| 硬约束 | 温度/季节不冲突 | 20/20 |
| 硬约束 | 套数符合 expect（含"不足时如实少出"） | 20/20 |
| 硬约束 | 输出 100% 可被 Pydantic 解析 | 20/20 |
| 软指标 | 「这套能穿出门吗」人工 5 分制 ≥4 分 | ≥16/20 |
| 软指标 | 理由引用了真实属性（温度/正式度/颜色至少 1 个） | ≥18/20 |
| 性能 | 单次生成 P95 | ≤12s |
| 降级 | 4 条失败 case 各自命中正确降级路径 | 4/4 |

**首次跑批正常成绩：13–16 / 20**。如果一次就 20/20，八成是 case 太软或断言写松了，回去加严。

### 你的验收动作

1. **亲手跑 2 条 case 的原始请求**，确认不是"脚本自己造了个通过"。
2. **看失败明细里有没有"期望值写错"的情况**——这是常见的假失败，改 expect 要单独 commit。
3. **看 4 条失败 case 是否真的走了对应分支**（日志里有 `fallback=...` 标记）。

### 常见翻车

- **把 case 断言写成"方案数=3"就完事** → 太软，20 条全过也没意义。要求每类至少一条断言打在"必须包含/必须排除具体单品"上。
- **声称通过但不给报告文件** → 要求 `docs/reports/eval_v1.md` 落盘，报告不存在就等于没测。
- **evaluate.py 里 try/except 全捕获后记 pass** → 这是最坏的情况，立刻查代码。

### 收口

```bash
git add -A && git commit -m "test: 20 条评测集 + 跑批脚本，首轮 14/20"
```

## 阶段 5 · BUG 改进（用失败样本驱动，三轮收敛）

### 目标

每一轮只修**一类根因**，修完立刻重跑，留下 `eval_v1 → v2 → v3` 的通过率曲线。**这条曲线就是简历里最有说服力的一行。**

### Prompt（第一轮，整段复制）

```
打开 docs/reports/eval_v1.md，只看失败的那些 case。

第一步，先做归因表，不要改代码：
case_id / 实际输出关键差异 / 根因分类(IN|FILTER|COMPOSE|PARSE) / 影响 case 数 / 修法 / 回归风险
按「影响 case 数」从多到少排序。

第二步，只修其中影响最大的那一类根因。
要求：
- 一次只动这一类，其他失败 case 先不管（写进 backlog）
- 改动前说明会碰哪些文件，改完说明为什么这样改能解决这一类
- 修完立刻重跑 evaluate.py，生成 eval_v2.md
- 对比 v1/v2 的通过率，并检查**原本通过的 case 有没有被改坏**（回归）

第三步，按 AGENTS.md §8 汇报，并回答：
- 这轮修完，还有几类根因没解决？
- 下一轮你建议修哪类，为什么？
```

### 后续两轮

同上，把 `eval_v1` 换成 `eval_v2` / `eval_v3`，并在开头加一句：

```
注意：本轮只准改 <根因分类>，上轮修好的部分不许回退。如果发现修复必须改动已通过 case 的逻辑，先停下来告诉我。
```

### 三轮之后写复盘（这次你自己写，不要让 AI 写）

`docs/reports/iteration-log.md`，格式固定：

| 轮次 | 修了什么根因 | 通过数 | 关键改动 | 引入的回归 |
|---|---|---|---|---|
| v1 | — | 14/20 | 基线 | — |
| v2 | FILTER：温度带用了硬阈值，15℃ 边界两边都排除 | 17/20 | 改成区间重叠判定 | 无 |
| v3 | PARSE：模型偶发返回 markdown 代码块包裹 | 19/20 | 加 extract_json + 重试 | C11 误判 1 次，已修 |

> 这张表是**你和"只会调 API 的人"的分水岭**。它证明你有"从失败样本反推系统缺陷"的能力，而不是"改到能跑就提交"。

### 常见翻车

- **一次把所有失败都修了** → 通过率涨了但你说不清是哪处改动起的作用，复盘写不出来，面试讲不了。
- **为了通过而放宽校验器**（把"必须衣柜内"改成"尽量衣柜内"）→ 这是红线，直接 revert。校验器是项目的可信度来源，宁可 case 失败。
- **只修 case 不修同类问题** → 要求它说明"这个修法对其他 70 种场景是否成立"，否则就是过拟合到 20 条 case。

## 阶段之间的节奏建议

| 阶段 | 建议时长 | 卡住的信号 |
|---|---|---|
| 1 需求对齐 | 0.5 天 | 10 个问题里超过 3 个你答不上来 → PRD 还没读透，回去读 |
| 2 方案输出 | 0.5 天 | 数据模型改了三版还在动 → 说明链路没想清，回阶段 1 |
| 3 确定 MVP | 0.5 天 + 4–5 天编码 | 单个任务反复超 1 天 → 任务切分有问题，重切 |
| 4 项目测试 | 1 天 | 首轮就 20/20 → case 太软 |
| 5 BUG 改进 | 1.5 天（3 轮） | 三轮通过率不动 → 根因归错了，重做归因表 |

总计 **8–9 个工作日**。如果只有 3 天，砍掉 P1 全部，P0 只做「手动录入 8 件 + 生成 3 套」，**但 20 条 case 一条都不能少**——功能可以少，证据不能少。

---

## 一句话总结这套流程的设计意图

> 需求对齐阶段**禁止写代码**，是为了逼出你的产品判断；
> 方案输出阶段**先出图纸**，是为了让后面的返工发生在纸上而不是代码里；
> MVP 阶段**一次一个任务**，是为了让每次 commit 都能独立回滚；
> 测试阶段**先定标准再跑**，是为了防止"跑完了再定标准"的自欺；
> 改进阶段**一轮一类根因**，是为了让通过率曲线能解释、能讲。
