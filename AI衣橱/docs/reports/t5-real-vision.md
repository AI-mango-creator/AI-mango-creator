## 三个必须写进代码的真实发现

### 1) 输出会带 Markdown 围栏 —— 解析前必须剥离

7 次返回里有 3 次是 ```json ... ``` 包裹的，不是裸 JSON。若解析器直接 `json.loads(text)`，这 3 次会全部判为 `PARSE` 失败（42% 的假失败率）。
做法：解析前 `text.strip()` 后剥离首尾 ```json / ``` 围栏，再 json.loads。剥离本身要进单测。

> 样本扩大后比例上浮：R01–R09 九条录制中 6 条带围栏（67%）。
> 见 `docs/reports/t5c-recognition-baseline.md`。**这个比例只说明"必须剥"，不用于推断总体分布**。

### 2) 高置信度不等于正确 —— 冲锋衣被标成 warmth=1

灰色冲锋衣（三层压胶、带帽、厚实）被判为 `warmth=1`，同时 `confidence=0.98`。
**这是本次最重要的发现**：现有 `needs_confirm` 阈值是 `confidence < 0.6`，这类"高置信度但错"的样本完全拦不住。

影响是功能性的：`warmth=1` 的 outer 在 8℃ 冷带会被过滤规则排除（cold 带要求 outer warmth≥2），
结果是"用户明明有厚外套，系统说没有厚外套，还提示你缺件"。

处理方向（不在 T5 里改算法，只记录）：
- 产品侧：编辑入口必须能改 `warmth`？——**不改**，D8 已定 `warmth` 不开放给用户（它是规则引擎依据）。
- 因此只能靠 prompt 校准 + 类目先验：`outer` 类目下 `warmth` 下限抬到 2（外套不可能是"极薄"），
  由代码做一次**类目-属性一致性校正**，而不是相信模型的单字段输出。
- 归因：这是 `IN`（识别错）类，T10 跑批时要能被单独统计，不能混进 compose 失败。

### 3) `warmth` 与 `seasons` 会互相打架

模型给冲锋衣 seasons=`[spring, autumn, winter]` 但 warmth=1——两个字段内部不一致（冬装不可能极薄）。
说明 prompt 里对 `warmth` 的锚点不够强。T5 的 prompt 要给出更硬的判定规则（例如"带帽、有内衬、压胶 → warmth≥3"），
并把"类目内 warmth 下限"这条一致性校验收进 `extract.py`，作为**代码侧后处理**，而不是指望模型自洽。

## 与验收标准的关系

T5 原判据：传咖啡杯 → 422 NOT_CLOTHING；传衬衫 → confidence>0.8 且 9 字段齐全；非 JSON → 重试 1 次后 IN 归因。
本次实测补充了第 4 条事实：**真实模型输出带围栏、且存在高置信度错误**。
因此 T5 的验收要增加两条：
- 剥围栏后解析成功率 7/7；
- `outer` 类目 warmth 下限校正生效（冲锋衣那件校正后 warmth≥2，不再被冷带误排除）。
